# x-writing

X向けの日本語投稿を作る。

目的は「短くすること」でも「バズる型に押し込むこと」でもない。
**元素材から一番強い一つの芯を選び、本人の声を残したままXで読める投稿へ作り直すこと**である。

note記事から作る場合も、本文の要約を機械的に短くしない。
同じ記事からでも、主張、体験、ユーモア、記事導線など別の入口を作れるようにする。

## 0. 優先順位

1. 今回のユーザー指示
2. `../../style-profile.md`
3. この `x-writing`
4. `../natural-japanese/SKILL.md`

外部の成長ハック、テンプレ、アルゴリズム説より、この順序を優先する。

## 1. 必ず併用するもの

### 常時

- `../../style-profile.md`
- `../natural-japanese/SKILL.md`
- `references/voice-and-humanizer.md`
- `references/audit.md`

### 依頼別

- 新規投稿・フック作成 → `references/hooks.md`
- note・ブログ・長文から再利用 → `references/repurpose.md` + `references/hooks.md`
- スレッド → `references/threads.md` + `references/hooks.md`
- 他人または自分の投稿のフック分析 → `references/hooks.md`

外部設計の出典と採用・不採用理由は `SOURCES.md`。

## 2. モード

### write

テーマ、メモ、口述素材からX投稿を新規作成する。

手順:

1. 一投稿で残す一つの芯を決める
2. `hooks.md` で複数の入口を内部比較する
3. 本文を書く
4. `voice-and-humanizer.md` で本人の声を守る
5. `audit.md` を通す

### repurpose

note、ブログ、長文、授業メモなどからX向けへ再構成する。

`references/repurpose.md` を使う。
コピー&短縮ではなく、元媒体の殻を外して一つの主張・体験・数字・場面を主役にする。

### thread

順番に読むことで理解や納得が深まる内容だけをスレッド化する。

`references/threads.md` を使う。
単に文字数に収まらないという理由だけでスレッドへ逃げない。

### hook-study

ユーザーが参考にしたいX投稿や文章を示したとき、その**表現ではなく構造**を分析する。

返すもの:

- フックが使っている仕組み
- 何を最初に見せているか
- 本文がどう約束を回収しているか
- 単発かスレッドかの判断
- ユーザーのテーマに移せる空の構造
- コピーすると危険な表現・誇張

他人の特徴的な文言をそのまま再現しない。

### audit

既存投稿を書き換えずに点検する。
`references/audit.md` の P0 Blocker / P1 Warning で返す。

ユーザーが「直して」と言った場合だけ修正版まで作る。

## 3. 標準出力

ユーザー指定がなければ `write` と `repurpose` では4案を出す。

1. **主張型** — 一番伝えたい考えを前へ
2. **体験型** — 実際の経験・観察がある場合だけ
3. **ユーモア型** — 元素材にあるズレ、自虐、可笑しさを使う
4. **note誘導型** — note素材の場合。投稿単体でも価値を残す

4案は語尾違いにしない。
**入口・主役・温度が違う4投稿**にする。

note URLが与えられていない場合は架空URLを入れない。

## 4. 一投稿一アイデア

一投稿で一番残したいものを一つ決める。

候補:

- 一つの主張
- 一つの体験
- 一つの数字
- 一つの場面
- 一つの反論
- 一つの笑えるズレ

全部入れたくなったら、削るか別投稿に分ける。

「情報量が多い = 良い投稿」ではない。

## 5. フック

フックは本文の外から貼らない。
元素材の中から一番強い材料を探す。

詳細は `references/hooks.md`。

特に守ること:

- 本文が回収できない約束をしない
- 元素材より強い断定にしない
- 根拠のない「最強」「絶対」「99%」を足さない
- 同じ逆張りテンプレを毎回使わない

## 6. 長さとX現行仕様

短文投稿を既定とするが、固定文字数を目的にしない。
日本語中心の短い投稿では、上限ぎりぎりまで詰めず余白を残す。

厳密な投稿可否が必要な場合は、文字数上限、URL、Premium長文、添付など**その時点のX公式仕様を確認する**。
仕様変更の可能性がある数値を恒久ルールにしない。

情報を削ると意味が壊れる場合だけ `thread` を検討する。

## 7. X向けのリズム

- 読点で会話の間を大量に作らない
- 一文を長くしすぎない
- 短文を機械的に連打しない
- 改行は意味の切れ目に使う
- 絵文字は必要な場合だけ
- ハッシュタグは必要な場合だけ
- CTAや問いかけを毎回付けない
- AIっぽさを消すための不自然な“パンチ行”を挿入しない

本人の癖と一般的なAI臭を区別する。
詳細は `references/voice-and-humanizer.md`。

## 8. 事実とハルシネーション

次を厳守する。

- ユーザーが言っていない指導人数、実績、資格、失敗談を足さない
- 元素材にない数字、固有名詞、会話を足さない
- 研究、制度、現在の仕様は必要なら確認する
- 確認できない事実は断定を弱めるか削る
- 元記事の誇張をさらに強めない
- 引用元のない名言や「研究で証明」を作らない

短文化で条件や例外を落とし、意味を反転させるのもハルシネーションとして扱う。

## 9. Humanizer

「AIっぽい語を全部禁止」のような機械処理はしない。

優先するもの:

1. モデル内部記号やテンプレ残骸を除去
2. 元素材にない創作を除去
3. 反復するAI定型を必要な箇所だけ直す
4. 修正後に本人の声を壊していないか確認

問題がなければ直さない。

AI detectorを通過すると保証しない。
詳細は `references/voice-and-humanizer.md`。

## 10. note-writingとの連携

`../note-writing/SKILL.md` から呼ばれた場合は、完成したnote記事を元素材として `repurpose` を実行する。

標準では:

- 主張型
- 体験型
- ユーモア型
- note誘導型

の4案を返す。

note本文と同じ順番・同じ構成にする必要はない。

## 11. アルゴリズム情報の扱い

「Xではこの型が伸びる」「リンクは絶対返信へ」「○文字が最適」のような情報を恒久的な文章ルールにしない。

必要な場合だけ現行情報を確認し、次を区別する。

- **文章品質として妥当な原則**
- **現在のUI・仕様**
- **第三者の経験則**
- **未検証のアルゴリズム推測**

最後の二つを事実のように扱わない。

## 12. 最終チェック

出力前に `references/audit.md` を使い、最低限次を確認する。

1. 元素材にない体験や数字を足していないか
2. 一投稿一アイデアになっているか
3. 一文目だけで何の話か分かるか
4. フックの約束を本文が回収しているか
5. noteの機械的な要約になっていないか
6. 複数案が本当に違う入口になっているか
7. 読点・短文・三項列挙などを人工的に増やしていないか
8. URLを捏造していないか
9. 投稿単体でも最低限の価値があるか
10. 書き手本人が自然に言いそうか

P0があれば修正してから出す。
